## 2026-08-14

- **RustDesk now runs in Desktop Mode only, and never at boot.** Chasing a "display dims and frames catch up every ~3 s" report during a game turned up `rustdesk.service` burning **80% of a core permanently** (621 s of CPU in 778 s of uptime) at **520 forks/s** — 275,384 forks in 529 s, from `/proc/stat`. Cause: Game Mode has no `RemoteDesktop` portal, so `--server` falls through to an X11 path with no `DISPLAY`, and instead of backing off it re-runs an 8-process shell pipeline (`ps -u 1000 -f | grep Xwayland | … | cat /proc/__/environ | grep WAYLAND_DISPLAY`) about 65 times a second, forever. Every iteration walks all of `/proc` under the task-list lock, so the cost *scales with what else is running* — worst exactly when a game is loaded. Invisible to `top` and to `ps` sampling (no child lives long enough); found via `cminflt` deltas in `/proc/<pid>/stat`, which charge reaped children back to the parent.
- **The gate is event-driven, not polled.** A systemd *user* unit `rustdesk-desktop-mode.service` is `WantedBy=plasma-workspace.target` — `static`, and pulled in only by a Plasma session, where Game Mode reaches `gamescope-session.target` instead. `PartOf=` makes it stop on the way out. `rustdesk.service` lost its `[Install]` section entirely, so `systemctl enable rustdesk` now fails loudly rather than quietly restoring the boot-time start, plus an `ExecCondition=` backstop against a manual start. `loginctl … -p Type` is useless as a discriminator here (answers `wayland` in both modes); `-p Desktop` is what the backstop reads (`gamescope` vs `KDE`).
- **New in `system/rustdesk/`:** `bin/rustdesk-in-desktop-mode`, `systemd/user/rustdesk-desktop-mode.service`, `polkit-1/rules.d/60-steam-machine-rustdesk.rules` (lets `deck` start/stop that one unit — three verbs, one user, no wildcards) and `atomic-update.conf.d/steam-machine-rustdesk.conf` to keep the rule across an A/B update. Without the keep entry the failure is hard to read: the service silently never starts and `systemctl status rustdesk` shows a healthy inactive unit, because the refusal lands in the *user* manager. `install.sh` gained `ensure_etc_config`/`ensure_user_unit` self-heal, removes the stale `multi-user.target.wants` symlink on upgrade, and `--status` now reports the gate, the polkit rule and the current mode instead of a meaningless `is-enabled`.
- **`install.sh --boot` moved from boot to Desktop Mode entry** as a consequence — it is the unit's `ExecStartPre`. Better placed: the `/usr` restore and the runtime firewall rules are needed only when the service is about to run, and a boot into Game Mode now costs nothing where it previously cost a package extract after every OS update.
- **Not the cause of the visible pulsing, as it turned out.** That was the `decky-clipboard` plugin polling the X clipboard every 2 s, spawning `sudo` + `xclip` against `DISPLAY=:0` four times per poll — each an Xwayland round-trip that can knock gamescope out of direct scanout. Uninstalling it fixed the symptom while RustDesk was still spinning at ~500 forks/s. Recorded because the diagnosis initially led the wrong way: a large constant load and a small periodic one look similar in a journal, and only the *periodicity* matched what was on screen.

## 2026-08-10

- **Added `lib/elevate.sh` and wired it into all 16 scripts that need root.** Run one unprivileged and it now re-runs itself under sudo instead of printing instructions. The prompt method is chosen at runtime, which is the part that actually matters here: a TTY (**including SSH**) gets plain `sudo` prompting in the terminal, while a shell with no TTY (Game Mode, an agent shell, a systemd unit) gets `sudo -A` with ksshaskpass on the TV. `sudo -A` cannot work over SSH — there is no GUI for the helper to draw in — so the old blanket "use `sudo -A`" advice was wrong for half the ways these scripts get run. Elevation is best effort: `inspect-link.sh` carries on with the link-state rows marked unknown, installers call `need_root` and die with an explanation. `--no-sudo` opts out.
- **`set -e` bug found while testing that.** A bare `elevate "$@"` returning non-zero aborted the calling script on the spot, so a declined or unavailable elevation surfaced as sudo's own two-line error and nothing else — the explanation was never reached. Needs `|| true`, now commented as load-bearing.

- **Tested a second DP→HDMI converter (ULT-W11Q) and found it is the same chip as the first.** It reports `branch OUI 0x2B02F0` / device ID `CH7218` — the identical `branch_dev_id` amdgpu printed for the UGREEN 80397 on 2026-08-02. Different product, same Chrontel silicon, so every converter-era conclusion carries over unchanged and a better adapter is not something shopping will find. New doc `hardware/display/4k120-paths.md` compares all three paths (native HDMI FRL / UGREEN / ULT-W11Q) with measured numbers.
- **CEC works over the converter, and cannot ever work on the native HDMI port.** `/dev/cec0` appears via the DP AUX tunnel (`drm_dp_cec`): CEC 2.0, physical address `2.0.0.0`, and the C9 answers with vendor `0x00e091` and power status. SteamOS's own `cecd` picks it up unaided (`rc0` = `rc-cec`, plus `cecd DP-1` input devices). amdgpu implements no HDMI CEC at all, which is the real reason the `steamos-cec-toolkit` was inert before it was removed.
- **Established exactly why VRR is refused through the converter, and that the adapter is not at fault.** `dm_get_adaptive_sync_support_type()` needs three conditions; two are met and measured (`ADAPTIVE_SYNC_SDP_SUPPORT`, DPCD 0x2214 bit 0 = 1; `allow_invalid_MSA_timing_param`, DPCD 0x007 bit 6 = 1) and the third is a hardcoded five-OUI whitelist in `dm_is_freesync_pcon_whitelist()` that `0x2B02F0` is absent from. The TV's real EDID reaches the GPU intact, HF-VSDB `VRRmin 40` / `VRRmax 120` included, and is discarded. Also corrected a stale assumption: **`freesync_pcon_allow_all` does not exist on mainline 7.2-rc6** — it is a downstream parameter, so the 2026-08-02 bypass cannot be repeated on the current kernel.
- **Recorded a quality regression that is probably not the hardware.** Same chip, but the UGREEN ran HBR3 at 16 bpp DSC while the ULT-W11Q sits at HBR2 at 12 bpp (2.5:1), with `link_settings` showing HBR3 verified and then trained down. The bandwidth arithmetic shows the two are a matched pair — 16 bpp needs HBR3, 12 bpp fits HBR2 — so it is one driver policy decision, and the suspects are the kernel (7.2-rc6 vs Valve 6.16) or the DP cable, not the adapter. Untested.
- **Added `hardware/display/inspect-link.sh`.** Read-only capability report on any connected HDMI or DP connector — sink EDID features (VRR range, ALLM, HDR10/HLG/DV, max FRL and TMDS), link rate, DSC state and ratio, FRL, converter identity, the three VRR preconditions decoded from DPCD, CEC — and scores the link **out of 10**. Runs unprivileged with the link-state rows marked unknown; root fills them in. Rates *available* capability rather than what an app is using at that moment, since HDR and wide gamut are toggled per app. Any unknown component scores 0 and the total is labelled a floor rather than a rating.
- **The scorer refuses to score a sleeping TV, which is the whole reason it exists.** With the C9 in standby the converter holds HPD and serves EDID from cache, so DRM reports `connected`, `enabled` and **53 modes** — indistinguishable from a healthy 4K120 link, and every derived number is fiction. CEC is the one honest channel: the TV answers `GIVE_DEVICE_POWER_STATUS` with `standby` in ~20 ms while asleep. The script asks first and stops with an explanation, since a plausible-looking score against a dark TV is worse than no score. `--force` overrides for the no-CEC case, with a warning.
- **Fixed `hardware/kernel/install.sh --status` producing no output at all as an unprivileged user.** `efi="$(efi_dir 2>/dev/null || echo '?')"` could never work: `efi_dir` ends in `die`, which exits the subshell before the `||` is reached, so the assignment failed under `set -e`. The ESP is `0700 root`, so this tripped on every non-root run — exit 1, nothing printed. It also made `grub custom.cfg` report `NO`, which reads as a missing boot entry, when the truth was an unreadable ESP; that now reports `?` with the reason.

## 2026-08-08

- **Added `system/portproton/`: PortProton's default wine version now tracks the newest installed GE-Proton automatically.** The setting is `PW_WINE_USE`, and it can only live in one of two places — `data/scripts/var:48`, which PortProton rewrites on every update, or `data/user.conf`, which is user-owned and sourced after it (`start.sh:208`). Set to `GE-PROTON11-3` there. Downloading a new GE-Proton does not update it, so a systemd **user** path unit watches `data/dist` and a companion service (also `WantedBy=default.target`, for builds that landed while logged out) rewrites the line. The path unit fires when the directory is created — the *start* of extraction — so `--update` requires both `proton` and `files/bin/wineserver` to exist and then waits for the tree to stop changing for 10s before writing. Verified end-to-end with a synthetic `GE-PROTON11-4`: switched to it in 10s, switched back when removed. `# pinned` on the `user.conf` line opts out. Existing games keep their own `.ppdb` version (sourced after `user.conf`) on purpose. No `--boot` and no keep entry — script, units and `user.conf` are all in `/home`.
- **Verified the `0007`/`0008` hid-steam patches reproduce the tree that built the working module,** rather than assuming it: all eight patches reverse-apply cleanly against `build72`, so the files in `patches/` are byte-exact against the sources `hid-steam.ko` was compiled from. Moved the `.BTF` trap out of this changelog and into `patches/README.md`, where a rebuild will actually be read — a freshly built module fails to load with `BTF: -22` until `objcopy --remove-section=.BTF` strips it, and the read-only rootfs plus the stale cache bite at the same moment.
- **Fixed `hardware/kernel/install.sh --status` printing nothing and exiting 1 unless run as root.** `efi="$(efi_dir 2>/dev/null || echo '?')"` cannot work: `efi_dir` ends in `die`, which exits the command substitution outright, so the `|| echo '?'` is never reached and the assignment fails under `set -e`. The ESP is `0700 root`, so every unprivileged run hit it and the entire status report — cache freshness, blacklist, VT unit — was invisible. The same unreadable ESP also made `grub custom.cfg` report `NO`, which reads as a missing boot entry rather than "cannot see the ESP"; it now reports `?`.
- **Found why the RAM RGB came back on after the SteamOS update: the marker that records "SMBus access granted" was not on the keep list.** `install.sh` writes an empty `/etc/udev/rules.d/.steam-machine-rgb-i2c` when the SMBus stanza is installed, and `--boot` reads it to decide which form of the rule to restore. `/etc/udev/rules.d` is not on `atomic-update-keep.conf`, so the update took the marker with it and the boot self-heal silently reinstalled the rule in its `--no-i2c` form: `/dev/i2c-2` lost the `deck` ACL, OpenRGB dropped from two devices to one, and `steam-machine-rgb-off.service` logged `Kingston Fury DDR5 not detected (no SMBus access?) -- skipping` while still exiting 0. **A self-heal that restores the wrong variant is worse than one that fails** — every unit reports healthy and the only symptom is LEDs. Marker added to `atomic-update.conf.d/steam-machine-rgb.conf`; README's "what survives what" table and self-heal paragraph corrected.
- **Made `install.sh --cache` say what it actually does, and made `--status` catch a stale cache.** The usage text called it "(re)build the cache tarball from a kernel build tree", which reads as a build-time step; it in fact snapshots the **installed** `/usr/lib/modules/<kver>`, and that tarball is the only thing an A/B update leaves behind. So any module added after the last `--cache` — `hid-steam` being the case that prompted this — is silently reverted at the next OS update, with no symptom beyond a missing device node. `--status` now diffs the installed tree against the tarball's mtime and prints `cache freshness: STALE` with up to three of the files that would be lost, plus the command to fix it. Kernel README updated to match.
- **Recorded that SMT is off in the BIOS.** The 9800X3D is 8C/16T and this machine runs 8C/**8T**: `Thread(s) per core: 1`, `smt/control` = `notsupported`, `thread_siblings_list` = `0`, and no `nosmt` on the kernel command line, so it is firmware-level. Noticed while a kernel build sat at 95% CPU across only 8 workers; costs roughly 25-40% on compile-bound work and is near-neutral for gaming. Added as a TODO plus a Platform notes section, because it silently halves throughput and skews any CPU benchmark taken before it is fixed.
- **Backported Valve's 2026 Steam Controller driver onto mainline 7.2-rc6 as patches `0007`-`0008`.** Valve's `hid-steam.c` from `6.18.42-valve2` (`af6356cf2488`) **compiles unmodified against 7.2-rc6** — no API changes needed — so the FRL kernel can carry it. **Confirmed working**: all nine puck interfaces moved from `hid-generic` to `hid-steam` and `/dev/input/js*` appeared. Two non-obvious obstacles on install, both recorded: the rootfs is read-only again after a SteamOS update (`/usr/lib/modules` is on it), and the module first refused to load with `failed to validate module [hid_steam] BTF: -22` -- a `pahole`-generated BTF section the kernel's validator rejects, fixed by `objcopy --remove-section=.BTF` since BTF only serves BPF tooling. Not upstream: checked `torvalds/linux.git` and `hid/hid.git`, whose newest `hid-steam.c` commits are 6.15-era, with nothing referencing IBEX/PROTEUS/NEREID anywhere in public kernel git. Two traps recorded in `patches/README.md`: `hid-ids.h` must take only the four new defines (Valve's 6.18 header predates 7.2's Harmonix/RiffMaster IDs and breaks unrelated drivers), and neither their `Kconfig` nor `Makefile` is needed.

Its `btmtk` also still knows only MT7922/MT7961/MT7925, so the out-of-tree Bluetooth module is still required.

- **Cause of the power-off hang identified: `mt7921e` binding the onboard MT7902 Wi-Fi.** Mainline 7.2 added `14c3:7902` to the driver's PCI table (commit `c26319afb5fb`); Valve's 6.16 matches `14c3:7920` only, which is exactly why stock powers off cleanly and this kernel does not. Probe then fails — MediaTek have never published MT7902 *Wi-Fi* firmware, so `WIFI_RAM_CODE_MT7902_1.bin` loads with `-ENOENT` and the driver logs `hardware init failed` — but the device stays bound, and `mt7921_pci_shutdown()` is a bare call to `mt7921_pci_remove()`, which blocks forever on an MCU that was never brought up. **Not yet confirmed by an observed clean power-off**; the test is `modprobe -r mt7921e` then `systemctl poweroff`.

Costs nothing: there has never been a `wlan` interface on this machine, and Bluetooth is a **separate USB device** (`0e8d:7902`, `hci0`, `btusb_mt7902`).
- **`initcall_debug` is what found it, after seven eliminations found nothing.** `device_shutdown()` prints each device's name *before* calling its handler, but only under `initcall_debug` — which is mode `0644`, so it needs no rebuild and no reboot. `poweroff-test.sh` now sets it in every mode, and the frozen console ended `mt7921e 0000:08:00.0: shutdown`. Eliminating components could only ever say what the cause was not; this named it in one attempt.

The `--sysrq` argument that supported the S5 theory does not hold: SysRq-o bypasses systemd but still runs `device_shutdown()`.

Link is Down` was the last line for several runs, so the NIC looked implicated; unloading it removed the message and changed nothing. Most drivers print nothing at shutdown, so the last voluntary message only says which driver was chatty.

There is a display attached. Pressing `e` at the GRUB menu, deleting `splash quiet` and appending `plymouth.enable=0 ignore_loglevel` gives a one-boot-only edit with nothing written to disk, and the last line on screen at the hang should name the subsystem. - **Corrected an earlier wrong attribution.** The blank-screen boot that followed creating a `grubenv` was blamed on that grubenv. It has since happened again with no grubenv present, so the cause is something else: it correlates with the preceding **forced power-off** (the 4-second hold needed to escape the S5 hang) and clears on a second power cycle. Two for two. Now tracked as a separate failure in both `custom.cfg.in` and the README, rather than as a GRUB problem.
- **Found why all four hangs left no evidence: this kernel cannot record one.** `# CONFIG_PSTORE_CONSOLE is not set`, inherited from Valve's config — so the `ramoops` console backend does not exist, `console_size=4096` records nothing, and only a panic or oops could ever reach pstore. These are hangs, so pstore was never going to hold anything. SysRq at the hang is useless for the same reason the power button is (CPU halted, interrupts off), and `netconsole` would die when the NIC is torn down during shutdown. Rebuilding with `PSTORE_CONSOLE`, `PSTORE_FTRACE` and `PSTORE_PMSG` enabled so the next hang leaves its final kernel output in the reserved RAM at `0x83de80000`, which survives the forced power-cycle. Cache tarball backed up to `kernel.tar.zst.pre-pstore` first.
- **Confirmed the stock-kernel comparison was clean.** The stock 6.16 boot that powered off used the same command line in every respect that matters — `acpi_enforce_resources=lax` and `amd_iommu=off` were both present — differing only by Valve's `ttm.pages_min` (ignored on mainline) and this build's `amdgpu.dcfeaturemask=0x402`. - **The six FRL/VRR patches are eliminated by deduction, not assumption.** All of them are in amdgpu display code; `--no-gpu` unloaded amdgpu entirely, so none of that code was resident, and it hung anyway. Whatever this is, it is mainline 7.2 core code rather than anything added here.
- **Documented the two new amdgpu module parameters in 7.2** and what they are. `hdmi_hpd_debounce_delay_ms` (runtime-writable, default `0`, "1500 is common") filters short disconnect→reconnect HPD toggles that HDMI sinks generate entering and leaving power save — aimed squarely at this TV. `ptl` is the **Peak Tops Limiter** (`Documentation/gpu/amdgpu/ptl.rst`), a machine-learning throughput governor whose data formats are `I8`/`F16`/`BF16`/`F32`/`F64`/`F8`/`VECTOR`; boot-time only, default off, irrelevant to gaming, and Navi 48 exposes no `ptl/` sysfs directory. Also recorded the three Valve-only parameters mainline does not have — `allm_mode`, `hdmi_vrr_desktop_mode`, `freesync_pcon_allow_all` — which means there is **no ALLM knob upstream**; it rides the HF-VSIF path the VRR patches add.
- **`--sysrq` hangs too, so userspace is excluded.** Three independent paths now fail identically — `--plain` (systemd + amdgpu), `--no-gpu` (systemd, no amdgpu), `--sysrq` (no systemd, amdgpu loaded). Note that `--sysrq` does **not** reach the firmware unaided as first claimed here: SysRq-o still calls `kernel_power_off()`, which still runs `device_shutdown()`, which is where the hang actually was. It excludes systemd and the display driver, and nothing below them.

But `wtmp` writes its `shutdown system down` line when *systemd* finishes, which is exactly what it does for every one of these hangs; the script's own `--report` output says as much. Those two power-offs were never observed reaching S5. - Corrected `hardware/sensors/`, which listed "`i2c-dev` is deliberately not loaded" as one of three SPD write mitigations. SteamOS loads it itself via its own `ddcutil` and `fwupd` modules-load entries: all 21 `/dev/i2c-*` nodes exist, including the SPD bus. Only the `spd5118` binding stands between userspace and the EEPROMs, and that is bypassable with `I2C_SLAVE_FORCE`.

- Resolved the `fan5` contradiction in `hardware/sensors/` and `hardware/coolercontrol/`, which documented the case fan as fixed-speed and uncontrollable at ~1548 rpm while it was reading 0 rpm. Both descriptions were right in their moment: the CPU_OPT header was in PWM mode with a 3-pin DC fan, which sees a permanent 12 V and ignores duty. Setting it to Voltage/DC made it controllable but put the BIOS's ~20% duty below the fan's start-up voltage, so it stalls from standstill - forcing `pwm5` to 255 started it at 1513 rpm and it then sustained 1537-1562 rpm back under BIOS control. Whether a cold boot strands it at 0 again is untested and flagged in the docs.
- Fixed `rustdesk.service` failing every boot. `After=NetworkManager.service` waits for the daemon, not for the network: the unit ran 3 s before `enp9s0` got carrier, `lan_cidrs()` found no addresses or routes, and `ExecStartPre` called `die` - so the service was dead until a manual restart, with no firewall rules on 21118 and nothing listening. Found only because the first reboot since install happened. Now ordered after `network-online.target` and `firewalld.service`, with `Restart=on-failure` and a bounded 45 s poll in `--boot`, since IPv6 RA can still arrive after that target is reached.
- Fixed `system/rustdesk/` never appearing in the Desktop Mode application menu. The Arch package ships its `.desktop` files to `/usr/share/rustdesk/files/` and relies on `.INSTALL`'s `post_install()` to copy them into `/usr/share/applications/`. We exclude `.INSTALL` deliberately - it also overwrites our unit and runs `systemctl enable/start` - but never replicated the desktop-file copy. With no menu entry the obvious move is to install the Flatpak, which lands at `/app`, fails rustdesk's `is_installed()`, keeps a separate config and ID, and competes for 21118. `--status` now reports both the missing entry and any Flatpak alongside it.
