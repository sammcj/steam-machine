## 2026-08-03

- Added `system/btop/`: btop's GPU box, which looked like a setting that did nothing. btop 1.4.4 is built `GPU_SUPPORT=true`, but its only AMD backend is the ROCm SMI library, which SteamOS doesn't ship - so it found no GPU and *silently deleted* `gpu0` from `shown_boxes` on every exit, which is why toggling it in the options menu never stuck. `LD_LIBRARY_PATH` is useless here: strace shows btop only ever tries five absolute paths, never a bare `dlopen` by soname. Four are under `/usr` (rootfs), but the fifth is `/opt/rocm/lib/` - and `/opt` is a SteamOS offload mount on the home partition, so it's writable without unlocking the rootfs and survives updates on its own. First subsystem here that needs no keep entry and no boot self-heal; `--status` asserts the offload mount is still what it claims to be so that assumption can't rot silently. Installs one 4 MB `.so` (verified by SHA256), not the ~400 MB ROCm stack its package depends on - `readelf` shows it links only libstdc++/libm/libgcc_s/libc. Result: Navi 48 recognised, with utilisation, temp, power, VRAM and clocks.
- Recorded in `system/btop/` that CPU and GPU cannot be shown side by side: btop's box geometry is hardcoded, the only layout keys are `cpu_bottom`/`mem_below_net`/`proc_left`, and boxes always stack full-width (verified at 150 and 190 columns, including two GPU boxes). Noted the two workarounds and why neither was applied - `show_gpu_info = "On"` splits three ways because the Raphael iGPU can't be hidden (`ROCR_`/`HIP_`/`RSMI_VISIBLE_DEVICES` all tested, none has any effect, since rsmi reads sysfs directly rather than going through the HSA runtime).
- Fixed a miscount in `system/btop/install.sh --status`: `find /sys/class/drm -name 'card[0-9]*'` counts connectors like `card1-DP-1` as GPUs, reporting 12 cards instead of 2. Now anchors on the `device/driver` link being `amdgpu`.
- **Correction:** `/root` is *not* on the rootfs and is *not* wiped by A/B updates. It's a SteamOS offload mount on the home partition (`/dev/nvme0n1p8[/.steamos/offload/root]`), writable regardless of `steamos-readonly`. Yesterday's `system/htop/` notes claimed the opposite, inferred from the rootfs mount without ever checking `/root` itself. Corrected across the README, install.sh and the keep-list comment. `/opt`, `/srv`, `/nix`, `/var/log` and `/var/lib/flatpak` are offloaded the same way - the general lesson being that "outside /home is disposable" is wrong on SteamOS, and `findmnt | rg offload` is the check. The `/etc/htoprc` mechanism itself still stands: `/etc` genuinely is an overlay whose upper layer an update discards, so the allowlist and self-heal are still doing real work - they were just never rescuing root.
- Added `system/htop/`: keeps the htop layout for both accounts. Only `root` is actually affected by OS updates - `/root` is on the rootfs subvol an A/B update replaces wholesale, so `/root/.config/htop/htoprc` is lost every time, and `/root` isn't writable under `steamos-readonly` anyway. Solved via `/etc/htoprc`, htop's read-only fallback, allowlisted with a boot self-heal, so nothing ever writes to `/root`. `deck` is *not* affected by updates (`/home` is a separate partition); its settings revert for two other reasons, both now checked by `--status`: htop only persists on a clean `q` exit (a signal discards the session), and a root-owned htoprc in deck's home from `sudo htop` makes every later save fail silently. Symlinking the repo file in was ruled out - htop writes via `mkstemp`+`rename`, which replaces the symlink. `--save`/`--apply` round-trip in-htop tweaks back to the repo. Installed and verified.
- Recorded in `system/htop/`: htop's per-core CPU **temperature** cannot work on this CPU. `k10temp` exposes exactly two sensors, `Tctl` (package) and `Tccd1` (die) - AMD has no per-core thermal sensors - so htop maps the one reading onto an arbitrary core and prints `N/A` for the other seven. `btop` showing a temperature on all eight cores is the same package number repeated, not more information. Per-core *frequency* does work; Text meter mode is far more legible than the bar. For temperature over time, CoolerControl on 11987 is already the right tool.
- Noted in `system/htop/`: `nproc` is 8 on a Ryzen 7 9800X3D (8C/16T) and `/sys/devices/system/cpu/smt/control` reads `notsupported` - SMT is disabled in firmware. Not a htop issue, recorded because it's the obvious thing to wonder about when the header shows 8 meters.
- Added `system/power/`: idle power tuning off the back of a `powertop` run. The prompt for it - "the CPU sits at 4 GHz+ all the time" - turned out to be a measurement artefact: `scaling_cur_freq` and `/proc/cpuinfo` derive from APERF/MPERF, which on AMD only tick in C0, so they report the awake-slice clock and cannot see halted time. Measured residency is 93% idle (77% C3). Only two of powertop's ~45 suggestions survived triage (`kernel.nmi_watchdog=0`, `vm.dirty_writeback_centisecs=1500`, via `/etc/sysctl.d` which is not on the keep list). `--status` measures package watts and C-state residency as deltas over an interval, and deliberately refuses to print `scaling_cur_freq`. The README records every rejected suggestion with its reason, so the next powertop run doesn't re-derive them.
- Found two CPU cores clamped at 603 MHz by an interrupted `powertop` calibration, and added a guard for it. `cpu0` and `cpu3` had `scaling_max_freq` = 603379 while the other six were at 5271622; all eight carried the same mtime to the millisecond (one writer looping over every CPU), inside an interactive `sudo powertop` session. powertop's binary has write paths for `scaling_max_freq`/`scaling_min_freq`/`scaling_setspeed` and a calibration mode that steps each core's range - it restored six and left two at the floor. No error, no log line, no kernel message; two of eight cores stay crippled until the next reboot, so the stutter arrives detached from the cause. `system/power/install.sh --status` now compares every core against `cpuinfo_max_freq` and warns, and `--restore-freq` fixes it without a reboot. Deliberately not in `--install`/`--boot`: at boot the policy is built from `cpuinfo_*` and cannot be clamped yet. **Run `--status` after any powertop session.**
- Cut `hardware/sleep`'s keep-awake grace window from 7200 s to 1800 s. At two hours it was costing more power than every tunable in `system/power/` saves: the journal showed only two suspends in three days, because the tail from one SSH session had not expired before the next began. 1800 matches Steam's own `IdleSuspendACSeconds` - a tail longer than the timer it defers is dead time.
- Corrected a backwards claim in `system/power/` and applied the tunable it wrongly dismissed. The README had the MX500s on `host4`/`host5` with `host0`-`host3` as empty ports; it is the other way round - `host0` = sda, `host1` = sdb, both at `keep_firmware_settings`, while the already-tuned `host4`/`host5` are empty. SATA link power management (`med_power_with_dipm`) is now set on all ahci hosts from a udev rule, allowlisted alongside the sysctls. `--status` prints the host-to-disk mapping on every run so it cannot be misremembered again, and counts ATA exceptions/link resets, since LPM misbehaving on these drives would surface as btrfs errors on the game library rather than as anything obviously power-related. Exercised after applying (256 MB write, then three cycles of 15 s idle + direct read, so the links actually had to wake): `iodone_cnt` rose on both drives, `ioerr_cnt` did not move, no ATA errors, `btrfs device stats` clean. Not proof - the failure mode is intermittent - so the ATA counter is the thing to watch over the next few weeks.
- Replaced the blanket "PCI runtime PM items are all pseudo-devices" claim in `system/power/` with the actual breakdown, after it was challenged. Runtime PM demonstrably works here - eleven devices (three `snd_hda_intel`, three `xhci_hcd`, several `pcieport`) are `auto` and *suspended* right now. Of the 41 "Bad" entries: ~20 have no driver bound so `auto` has nothing to invoke; five are the single fact that `0f:00.0` cannot suspend while its USB children are pinned `on`; the audio one is a powertop bug (it string-compares `power_save` against "1", the value is "10" and all three codecs are suspended); the SATA ones were real. Also documented why the remaining driver-bound candidates (SMBus, `k10temp`, iGPU, CCP) are deliberately left alone.
- Fixed a `set -euo pipefail` truncation in `system/power/install.sh --status`: `ls` on an empty SATA port exits non-zero and pipefail propagated it through the assignment, silently cutting the host table off at the first empty host.
- Fixed `hardware/sleep/install.sh` silently not applying config changes: it finished with `systemctl enable --now`, and `--now` degrades to `start`, which is a no-op on an already-active unit. The 7200 → 1800 window edit wrote the new unit file, reported success, and left 7200 live in the running daemon - and `--status` read the window from the unit file, so it confirmed a change that had not happened. Now `restart`s, and `--status` reports the *running* window (parsed from the daemon's own startup log line, filtered to the current MainPID) alongside the configured one, warning on drift. General trap for any unit carrying config in `Environment=`: `daemon-reload` makes systemd re-read the file, not the process.
- Fixed `hardware/sleep/install.sh` racing its own status block: after the restart above, `do_status` ran before the daemon's first loop iteration and printed "sleep currently held: no" with SSH sessions plainly open. Now waits up to 5 s for the inhibit unit, breaking early. A full timeout is also the correct outcome when there are no SSH sessions.
- Rejected USB autosuspend on the GIGABYTE ITE device (`048d:5711`) after initially recommending it. Nothing latency-sensitive polls it, but it is the IT5711 RGB Fusion controller `hardware/rgb/` writes to over hidraw to keep the LEDs off, and ITE controllers are known to revert to their hardcoded rainbow on USB suspend. Sub-watt gain against the living-room LEDs coming back on.
- Added `hardware/sleep/`: the machine was suspending out from under SSH sessions (Steam's Deck-UI sleep timer asking logind, not systemd idle). A root daemon now holds a logind `block` inhibitor on `sleep` while any sshd session exists, plus a 2 h grace window. Ships a polkit rule so `deck` can also take the lock by hand via a new `keepawake` shell function - without it a remote `systemd-inhibit` hangs on an unanswerable password prompt.
- Added `system/ssh/` (new top-level, since sshd isn't hardware): brings the previously untracked `/etc/ssh/sshd_config.d/10-steam-machine.conf` into the repo and allowlists it. The keep list covers `/etc/ssh/*_key` only, so `AllowUsers deck` and `PermitRootLogin no` would have silently reverted on the next A/B update. Also sets `ClientAliveInterval 60` / `ClientAliveCountMax 5` so dead SSH sessions are reaped in 5 min instead of up to ~2 h 11 m of TCP timeout - without which one dropped client would pin the machine awake via the inhibitor above.
- Added `hardware/network/`: Wake-on-LAN for the onboard RTL8125D, which was not armed at all (`power/wakeup` disabled, `wakeup_count` empty). Uses a `99-default.link.d` drop-in plus the NetworkManager `wake-on-lan` property - no `ethtool` needed. Still requires `ErP = Disabled` in the BIOS for wake-from-S5, which cannot be set from Linux.
- Added `system/rustdesk/`: LAN-only unattended remote desktop for Desktop Mode. Installs the upstream Arch package into `/usr` with a cache-and-restore under `/home` (rustdesk's `is_installed()` only accepts `/usr` or `/nix/store`, which also disqualifies the Flatpak). Access is restricted by RustDesk's own `whitelist` plus firewalld rich rules on 21118 - needed because the `public` zone allows 1024-65535 wholesale and this box has a routable IPv6. Note RustDesk cannot be stopped contacting its public rendezvous server without also disabling direct IP.
- Noted in `hardware/network/`: replaced the hardcoded MAC in the README with a placeholder, since the repo is public and `install.sh --status` prints it anyway.
- Added `system/firewall/`: blocks unsolicited inbound IPv6 from outside the LAN. SteamOS's `public` zone opens `1024-65535/tcp,udp` with no address-family restriction, and this machine has a globally routable IPv6 with a default route - so every service above port 1024 was exposed to whatever the router forwards. IPv4 is untouched (RFC1918 behind NAT). Established/related is accepted ahead of the drop, and the script refuses to install if it can't verify that in the live nftables chain. `--apply` is runtime-only with a 5-minute auto-revert, since a bad rule locks out the only remote path to a machine whose other console is the TV.
- Fixed `system/firewall/` pinning rules to point-in-time IPv6 prefixes. pfSense renumbered the ULA (`fd50:fdf7:233::/64` → `fde4:ff5:dc44:476e::/64`) and the stale rule silently began dropping LAN traffic on the new prefix. Link-local and unique-local are now generalised to `fe80::/10` and `fc00::/7` - neither is internet-routable, so allowing the whole range costs nothing. `--boot` now reconciles against live prefixes instead of only restoring when absent, so a GUA re-delegation self-corrects on the next boot rather than locking out IPv6 SSH indefinitely.
- Fixed `system/rustdesk/install.sh` writing config only to `/root`, which left `direct-server` unset and nothing listening on 21118. RustDesk's `--server` runs as `deck` and a 0.3s loop pushes user-side config *up* to root, so a pre-existing `~deck/.config/rustdesk/RustDesk2.toml` silently wins. Now stops the service, merges the options into both copies (preserving RustDesk's own keys rather than overwriting), and restarts.
- Fixed a `set -euo pipefail` bug that made `system/firewall/install.sh --apply` die silently on a first run: a `grep` matching nothing exits 1, failing the pipeline. Matching is now done in bash on a captured string. The same shape was fixed in `system/rustdesk/install.sh`; the other four installers were audited and are clean.
- Fixed three `--status` false negatives where an unprivileged check reported a root-only permission failure as breakage: the polkit rule in `hardware/sleep` (`/etc/polkit-1/rules.d` is 0750), `sshd -t` in `system/ssh` (can't read host keys, reports "no hostkeys available"), and the config/password checks in `system/rustdesk` (`/root` is 0700). All now say "unverifiable as <user>" instead.
- Armed WoL without a reboot (`--arm-now`); `power/wakeup` now reads `enabled` and udev is applying the drop-in. Added a remote test procedure to `hardware/network/README.md`: S3 first with an RTC alarm as an independent way back, `systemctl suspend -i` because `hardware/sleep`'s own inhibitor otherwise blocks it, and `power/wakeup_count` to tell whether the magic packet or the backstop did the waking - without which a successful-looking test proves nothing. Noted that the backstop does *not* cover the S5 test, since RTC-from-S5 and WoL-from-S5 both need the standby rail ErP cuts and fail together.
- Confirmed on the live session bus that Game Mode exports `ScreenCast` but not `RemoteDesktop`, so RustDesk cannot inject input there - the gamescope session redirects portal lookup to `gamescope-portals/`, where `kde.portal` is not a candidate at all. Documented in `system/rustdesk/README.md` as structural rather than a misconfiguration, along with the first-connection portal consent dialog, which makes "unattended" access require one click on the TV before it is actually unattended.
- Fixed `system/ssh/install.sh` containing unresolved merge conflict markers - the file did not parse, and its unit uses a bare `ExecStart`, so `steam-machine-ssh.service` would have failed at the next boot and stopped restoring sshd policy.
- Removed two hardware identifiers from this public repo: the live Bluetooth BD_ADDR (`README.md`, `hardware/bluetooth/README.md`) and the two DDR5 module serials in `hardware/sensors/baseline/`. `spd-check.sh` now hashes serials on both sides of its diff, so the SPD corruption canary still fires on a change without publishing the value. Both are still in pushed git history.
- Replaced `.gitleaks.toml`, which allowlisted paths from an unrelated project and had no rule for the identifiers that actually leaked. Now carries MAC and DDR5-serial rules.
- Closed a silent persistence gap in `hardware/storage/`: `/etc/systemd/system/*.timer` is not on the SteamOS keep list although `*.service` and `*.wants/**` are, so an A/B update would delete `steam-machine-dedupe.timer` and leave its wants symlink dangling - monthly dedupe stops with no error. Added a keep entry and an `ensure_units` self-heal in `--boot`.
- Fixed the amdgpu-in-initramfs guard in `hardware/display/install.sh` and `hardware/gpu/install.sh`. It tested `/boot/initramfs-$(uname -r).img`, which does not exist - Arch names the image after the pkgbase - so `lsinitcpio` read nothing, `grep -q` matched nothing, and the warning could never fire. Now resolved from `pkgbase`, with an explicit warning when the image cannot be found.
- Corrected `hardware/sensors/`, which listed "`i2c-dev` is deliberately not loaded" as one of three SPD write mitigations. SteamOS loads it itself via its own `ddcutil` and `fwupd` modules-load entries: all 21 `/dev/i2c-*` nodes exist, including the SPD bus. Only the `spd5118` binding stands between userspace and the EEPROMs, and that is bypassable with `I2C_SLAVE_FORCE`.
- Fixed `hardware/coolercontrol/README.md` hardcoding `hwmon4` in the PWM sweep recipe. hwmon numbering is probe-order and moves between boots - `it8696` was `hwmon9` and came back as `hwmon5` after the next reboot. The recipe resolves by chip name.
- Deleted `hardware/ram/rgb_disable-plan.md` (488 lines). Superseded by `hardware/rgb/` - none of its deliverables were ever built, its premise (a wrong i2c port) was wrong, and its central rule "never install or run OpenRGB" is the opposite of what shipped. A short tombstone in `hardware/rgb/README.md` keeps the reasoning.
- Corrected stale status in `README.md`: `acpi_enforce_resources=lax`, DIMM temps, GPU overdrive and OpenRGB RAM detection have all landed and were verified live, but were still marked as needing a reboot.
- Corrected `system/firewall/README.md`, which implied the installer validates rules against firewalld's parser at runtime. It does not - that check was done while writing it.
- Fixed `.git/hooks/pre-commit` hardcoding `/Users/samm/.venv/bin/python3`. The interpreter is now resolved at runtime and checked for the `pre_commit` module, so the hook works on both the macOS laptop and this machine. Note `pre-commit install` regenerates the hardcoded form.
- Fixed `hardware/sensors/install.sh` skipping the grub drop-in whenever the file merely existed and the parameter was live. Any later edit to the repo's copy silently never reached `/etc` - the installer reported success, changed nothing, and `--status` then showed drift that re-running could not clear. Now compares content.
- Fixed `system/rustdesk/install.sh` deriving its LAN allowlist from interface addresses only, so it never saw the RA-advertised ULA (on-link route, no address) and silently dropped RustDesk traffic over it. Now reads routes too and generalises to `fc00::/7` / `fe80::/10`, matching `system/firewall`. pfSense renumbered the ULA a second time during this work (`fde4:...` back to `fd50:...`), which is exactly what the pinned prefixes could not survive.
- Fixed `system/rustdesk/install.sh` adding firewall accepts without removing the previous set, so stale rules accumulated on every prefix change - generalising `fe80::/64` to `fe80::/10` left the old rule behind. `apply_firewall` now reconciles. A re-delegated GUA would otherwise leave an accept for a prefix belonging to somebody else.
- Resolved the `fan5` contradiction in `hardware/sensors/` and `hardware/coolercontrol/`, which documented the case fan as fixed-speed and uncontrollable at ~1548 rpm while it was reading 0 rpm. Both descriptions were right in their moment: the CPU_OPT header was in PWM mode with a 3-pin DC fan, which sees a permanent 12 V and ignores duty. Setting it to Voltage/DC made it controllable but put the BIOS's ~20% duty below the fan's start-up voltage, so it stalls from standstill - forcing `pwm5` to 255 started it at 1513 rpm and it then sustained 1537-1562 rpm back under BIOS control. Whether a cold boot strands it at 0 again is untested and flagged in the docs.
- Fixed `rustdesk.service` failing every boot. `After=NetworkManager.service` waits for the daemon, not for the network: the unit ran 3 s before `enp9s0` got carrier, `lan_cidrs()` found no addresses or routes, and `ExecStartPre` called `die` - so the service was dead until a manual restart, with no firewall rules on 21118 and nothing listening. Found only because the first reboot since install happened. Now ordered after `network-online.target` and `firewalld.service`, with `Restart=on-failure` and a bounded 45 s poll in `--boot`, since IPv6 RA can still arrive after that target is reached.
- Added CHANGELOG.md and a CLAUDE.md rule so future changes to the build notes and install scripts get logged.
