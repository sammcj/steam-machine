## 2026-08-06

- **4K 120Hz now runs over the native HDMI port** — built mainline **Linux 7.2-rc6** by hand and enabled HDMI 2.1 FRL with `amdgpu.dcfeaturemask=0x402`. Measured: **3840×2160 @ 120 Hz, RGB 4:4:4, 12 bpc, uncompressed (DSC off), HDR10, `underflow 0`, single pipe**, at a **1187.20 MHz** pixel clock — 1.98× the 600 MHz HDMI 2.0 TMDS ceiling. The UGREEN DP→HDMI converter is out of the chain. New `hardware/kernel/` subsystem with the full method, plus `frl-4k120-evidence.txt` holding the raw debugfs capture in both SDR and HDR states.
- **Proved no Valve kernel can do this**, rather than trusting release notes: `amdgpu.ko` extracted from `linux-neptune-616-drm-exec` 6.16.12, `linux-neptune-618-drm-exec` 6.18.33 and `linux-neptune-618` 6.18.38 all carry a **byte-identical** FRL symbol set, and none contain `dcn401_hpo_frl_stream_encoder`, `link_hdmi_frl` or `link_hwss_hpo_frl`. The `*frl*` symbols they do have belong to the DP-to-HDMI PCON path. Confirmation that the *native* path is what's now running: dmesg shows `hdmi_frl_status_polling_workque` and the DTN log's HPO block populates with `Lanes 4` / `Borrow ACTIVE`.
- **Two corrections to the widely-quoted incantation.** Every article says `amdgpu.dc_feature_mask=0x400`. The parameter is spelled **`dcfeaturemask`** (`dc_feature_mask` is the C variable), and it **replaces** rather than OR-s the mask — so `0x400` would silently clear the default `DC_MULTI_MON_PP_MCLK_SWITCH_MASK` (`0x2`). The correct value here is **`0x402`**.
- **Retracted a claim from 2026-08-02.** The converter result was recorded as "better than native FRL would have given". Tested, and it is not: native FRL gives 12 bpc uncompressed against the converter's 10 bpc with DSC. The original prediction was made against the 4:2:0 workaround, not against real FRL.
- **ODM 2:1 combine is not mandatory for 4K120 after all** — that was measured on the DP+converter path. Over native FRL the HPO block reports `ODM Segments 0` and every HUBP pipe is the full 3840 wide, not the ~1922 that ODM 2:1 produces. Same pixel clock, single pipe, no stitching.
- **`GRUB_TIMEOUT` does nothing on SteamOS.** Valve's "steamenv header sub block" hardcodes `timeout=0` in the generated `grub.cfg` and ignores `/etc/default/grub*` entirely, so no boot menu ever appears and an alternate kernel is unreachable. The override has to go in `/efi/EFI/steamos/custom.cfg`, which `/etc/grub.d/41_custom` sources ~130 lines later. Recorded because it will bite any future alternate-kernel or recovery work.
- **Boot safety, since the TV is the only console:** `GRUB_DEFAULT` pinned to the stock 6.16 entry by **id** rather than index (`10_linux` promotes the newest kernel to the top-level entry, which would have silently made the test kernel the unattended default). The FRL boot entry is defined in `custom.cfg` rather than via `GRUB_CMDLINE_LINUX`, so `dcfeaturemask` reaches only that kernel — a first attempt injected it into the stock 6.16 line too, caught by diffing the generated command line against the live `/proc/cmdline`. Rollback lives in `install.sh --uninstall`, which refuses to run from the probe kernel and refuses to finish if the stock kernel is missing from the regenerated config.
- **Gamescope HDR offload kept on a mainline kernel with a one-line patch.** SteamOS uses `CONFIG_DRM_AMD_COLOR_STEAMDECK` for AMD's driver-private per-plane colour properties. That code is *already upstream*, guarded by `#ifdef AMD_PRIVATE_COLOR`, a define mainline never sets — upstream's own docs say to build with `-DAMD_PRIVATE_COLOR`. Valve's commit is a 7-line Kconfig plus six `#ifdef` renames and conflicts on 7.2; one line in the `amdgpu_dm` Makefile does the same job. HDR confirmed active in a game: connector `Colorspace` flips `0` → `9` (`BT2020_RGB`), the exact test gamescope's `IsHDRActive()` uses.
- **Recorded the two remaining gaps and how to close them.** CEC still does not work — the native port did not fix it, because amdgpu registers no CEC adapter at all (a USB adapter is the only option today). VRR still does not work — 7.2 shipped FRL deliberately *without* HDMI VRR; that series lines up with 7.3.
- **The FRL kernel now survives a SteamOS update, and is the default boot entry.** `hardware/kernel/install.sh` gained `--install`/`--boot`/`--cache`/`--status`/`--uninstall`. A 172 MB artefact tarball on `/home` (kernel, all modules, and the rebuilt out-of-tree `it87` and `btusb_mt7902`) is restored by `steam-machine-kernel.service` — a `Type=oneshot` unit in `/etc/systemd/system/`, which **is** on Valve's `atomic-update-keep.conf` allowlist, so it is the one thing that survives an image swap and it reinstalls everything else. `custom.cfg` is *regenerated* rather than preserved, because an update can land you on the other A/B slot and a kept copy would carry the wrong rootfs UUID. Cost of an update is one boot on the stock kernel.
- **Architectural decision that makes this safe:** the kernel lives in `/boot/frl/`, not `/boot/`. `10_linux` globs `/boot/vmlinuz-*` non-recursively, so it never sees it, `grub.cfg` stays byte-for-byte stock, and the entire FRL boot path is one file. Delete `custom.cfg` and GRUB falls straight through to Valve's kernel. The `set default` in it is guarded by `if [ -z "${boot_once}" ]`, so `grub-reboot` one-shots still win. The 10-second menu is kept.
- **Self-heal tested by deleting each piece and re-running `--boot`** — which found a real bug: `install_preset` was gated behind the initramfs check, so a preset-only wipe restored nothing while reporting success. Split into `install_preset_file` and `regen_initramfs`. The full-wipe case was verified by extracting the tarball to a temp directory rather than pulling the running kernel's own modules out from under it.
- **VRR: nothing to build, and 7.3 does not exist.** Fetched `amd-staging-drm-next` (`d8ab7636160e`, 1034 commits ahead of `v7.2-rc6`) and the ALLM + HDMI VRR "Gaming Features" series (Pakuła, v4, 27 patches) is **not in it** — `allm_mode`, `hdmi_vrr_desktop_mode` and `freesync_pcon_allow_all` are absent from the whole staging tree, while appearing 3/2/3 times in Valve's 6.18. `amd-staging-drm-next` is the branch to re-check, not the mailing list.
- **CEC: confirmed not closable in software.** No module, parameter or debugfs knob registers an adapter; amdgpu has no CEC adapter implementation for its own HDMI ports at all. `hdmi_cec_state` reporting `1` is the *sink's* DDC-advertised capability. A USB adapter is the only route.

- **Ruled out, each checked rather than assumed:** InputPlumber (`inactive (dead)`); udev (`60-steam-input.rules` matches VID `28de` by wildcard, and the jupiter rules tag all hidraw `uaccess`); the host being mistaken for a Deck (DMI reports the Gigabyte board); a stale install (the `steamui` package was current as of 2026-08-02 — old chunk mtimes are preserved from the archive, not evidence of staleness).

It is not: `/usr/bin/steam-jupiter` passes `-steamdeck` in *both* sessions — provable from the flag ordering in `bootstrap_log.txt` — and the misidentification happens in both. The fallback is in the type mapping, not the session.

The in-client menu offers only Deck Stable and Deck Beta. Switching to Deck Stable was tried and did not help — and cannot, since stable is *behind* beta.

Upstream mainline has not added `1302`/`1304` either. Not the cause of anything above, and it would need a kernel change rather than anything droppable in `/etc`.

## 2026-08-04

- **Documented how to stop and start RustDesk** — `system/rustdesk/README.md` covered install, `--password`, `--status` and `--uninstall` but never the on/off switch, and there is no `--enable`/`--disable` front end the way CoolerControl has. New "Turning it on and off" section: plain `systemctl`, both states survive an A/B update (the enable symlink is keep-listed), and any `start`/`enable --now` re-applies the firewalld rich rules via the unit's `ExecStartPre=install.sh --boot` — which matters because those rules are runtime-only and do not survive a reboot by themselves. Also records that `stop`/`disable` leave the rules in place (only `--uninstall` removes them), so 21118 still appearing in `--list-rich-rules` is not evidence the service is up, and repeats the two traps: `stop-service = "Y"` is not the off switch (it kills the direct-IP listener and self-disables the unit), and `RustDesk2.toml` must be edited with the service stopped.
- **Added `system/shell/`** — the interactive-shell aliases and environment that were only ever in `~/.bashrc` are now in the repo: `bashrc.d/aliases.sh` (`vi`, the `cc`/`ccd`/`cccd`/`ccrd` Claude Code aliases, `g`/`p`/`P`/`gitwip`, `trigger_detect_tv`) and `bashrc.d/env.sh` (`~/.local/bin`, Homebrew `shellenv`, `DOTNET_ROOT`). Sourced from the repo rather than copied, same pattern as the three hardware subsystems that own a snippet, so the file under git is the one actually in use. `install.sh` is root-free, idempotent, and its `--uninstall` removes only the exact two-line block it wrote — a hand-edited block is reported and left alone. No keep entry and no `--boot` self-heal: `~/.bashrc` and the checkout are both on `/home`, which an A/B update does not touch.
- **`trigger_detect_tv` now calls `display-redetect`** instead of writing 0/1 to a hardcoded `/sys/kernel/debug/dri/0/DP-1/trigger_hotplug` — so it auto-detects the connected connector rather than assuming card 0 / DP-1, takes the lock, and is the identical script the four automatic triggers run. `--force` skips the 60 s debounce (it was typed deliberately) and `--tag manual` gives it its own stamp so a manual run can't suppress the controller-connect trigger.
- Verified by diffing the resulting environment against the pre-change `~/.bashrc` sourced in a clean `env -i` shell: `PATH` byte-identical (brew → `~/.local/bin` → system → `~/.dotnet`), `DOTNET_ROOT` identical, alias set identical apart from the two intended changes (`g` now absolute rather than `~`-relative, same target). Install/uninstall round trip restores `~/.bashrc` to its original content, and the hand-edit guard was exercised against a throwaway copy. `env.sh` guards on brew and `~/.dotnet` existing, so it is safe to source on a machine without either.
- Recorded rather than changed, since the repo is public: `gitwip` is `git add .` plus `commit -n`, so it stages whatever is untracked and skips pre-commit hooks — a gitleaks hook does not run. `.gitignore` already covers `gitleaks-report.json` and `.claude/`.
- **Repaired the unrelated-histories split between this machine and the laptop.** The rsync'd copy was re-committed from a fresh root (`A new start`), so `git pull` had no common ancestor. The remote tree was a strict superset of the local one (28 modified, 28 added, nothing deleted) and every overlapping untracked file was byte-identical, so `main` was reset to `origin/main`; the old 17-commit local history is kept as the tag `pre-rsync-local-history`, and gitignored content (`.claude/`, `gitleaks-report.json`) was untouched.
- **CoolerControl is now off by default, toggled per measurement session.** It was running permanently — a root daemon polling hwmon and the Super I/O with a LAN-reachable read/write API, for graphs that are only wanted while actually measuring something. `install.sh` now installs, starts the daemon once to verify the binary and config are sound, then disables it; `--enable`/`--disable` are unchanged and are what the new front end calls.
- **Added `hardware/coolercontrol/bashrc.d/coolercontrol.sh`** — a `coolercontrol` shell function (`on`, `off`, `status`, `ui`, `logs [N]`; `status` is the default), sourced from `~/.bashrc` by the installer following the same pattern as `keepawake` and `wayland-switch`. Picks sudo's own prompt on a real terminal and the graphical askpass when there is no TTY. Intended flow: `coolercontrol on` → reboot into gaming mode → measure → `coolercontrol off`.
- "On" persists across reboots on purpose (that is what makes the reboot-into-gaming-mode flow work), and the enable symlink is under `/etc/systemd/system/multi-user.target.wants/`, on the SteamOS keep list, so it survives an A/B update; "off" is the absence of that symlink and so survives trivially. `on` goes through `systemctl enable --now`, so the unit's `ExecStartPre` still re-asserts `apply_on_boot = false` before the daemon can act on a config an update may have reset. Verified on the machine: on → API answers on 11987 → off → `unit: disabled, active: inactive`, `pwm*_enable` still 2 (BIOS) throughout.
- **Diagnosed "TV shows no signal after a WoL boot with the TV off".** The DP sink is the CH7218 converter, not the TV: it holds HPD asserted and answers EDID from cache regardless of the TV's power state, so at boot gamescope saw `Connector DP-1 -> GSM - LG TV`, read its colorimetry and set 4K120 into a converter with nothing downstream. When the TV later wakes the converter never re-asserts HPD — **zero hotplug uevents across a boot containing three TV power cycles** — so nothing re-detects and the TV comes up to no signal while `DP-1 connected`, `crtc-0 active=1`, HBR3 4-lane, `dsc_clock_en 1`, `underflow 0` all report perfect health. Not boot-specific: any modeset or blank landing while the TV is off strands it the same way.
- **Proved there is no way to detect the TV's power state from this side**, rather than assuming it. Sampled across a TV power cycle (35 samples, 128 s): DPCD `SINK_COUNT` pinned at `0x41`; 2048 bytes of DPCD across eight pages bit-identical; the DP 1.4a protocol-converter status page all zeroes (the device reports DPCD **1.2**, so those registers do not exist); EDID answered from converter cache on DDC `0x50`; DDC/CI **absent at `0x37` in both states** (`ddcutil` reads the EDID but reports "Invalid display", `getvcp D6` returns `DDCRC_RETRIES`/`EREMOTEIO`); HDMI audio ELD unchanged. So a polling daemon has nothing to poll and the fix cannot be detection.
- **Added `hardware/display/bin/display-redetect`** — forces a replug via the connector's debugfs `trigger_hotplug`, which makes the compositor drop the output and re-detect it. A bare `echo 1` is **not** enough (measured): the connector never leaves the connected state so userspace re-probes, sees no change and does nothing. Has a lock, connector auto-detection, and a per-trigger debounce stamp — deliberately per-trigger, because a shared one would let the speculative fire at boot (useless if the TV is off) suppress the controller trigger seconds later, which is the one that matters.
- **Added four triggers:** Shift+Esc (`steam-machine-display-hotkey.service`, the escape hatch that works when the screen is already black), controller connect (udev rule matching the DualSense over USB *or* Bluetooth), boot (+25 s after `graphical.target`), and resume (+8 s after `suspend.target`). The hotkey daemon reads evdev directly rather than binding through xbindkeys or kglobalaccel, because it has to work in Game Mode, Desktop Mode and a bare TTY and survive a session switch; it inspects only `KEY_ESC` and the two Shift keys, logs nothing, and does not grab the devices.
- Persistence: the udev rule is added to the `atomic-update.conf.d` keep entry (`/etc/udev/rules.d` is **not** on the SteamOS default keep list) with a self-heal in `install.sh --boot`; the units are under `/etc/systemd/system/*.service`, which is keep-listed. The scripts run from the repo on `/home`, so nothing needs a rootfs unlock and an A/B update cannot delete them — hence `RequiresMountsFor=/home/deck` on every unit.
- Verified end to end on the machine: `udevadm trigger --action=add` on the DualSense's hid node started the unit and kwin re-detected `DP-1`; a second trigger 12 s later was correctly suppressed by the debounce; `install.sh --status` reports all four triggers.
- Not fixed, and recorded as such: picking up the controller *before* switching the TV on still fires into a dark TV and achieves nothing — Shift+Esc is the fallback. Waking the TV over the network is ruled out (it is deliberately off the LAN), as is reverting to the native HDMI port (real HPD, but 4K60 until amdgpu gets FRL on Linux 7.2+). The ordering that avoids the problem entirely is TV on first, then wake the machine.
- Re-derived the CH7218 identity from DPCD `0x500` during the investigation before noticing it was already documented from 2026-08-03. No new information; the genuinely new material is the power-state invisibility measurements above.
- Repeated yesterday's `pkill -f` self-kill (exit 144) — the pattern matched the command line running it. Yesterday's fix was to write test scripts to files instead of heredocs, which was done here; the trip-up was `pkill -f` against a *filename* still matching the invoking shell. Use `pgrep -f` with a bracketed pattern and kill by PID.

## 2026-08-03

- Fixed Steam's Power → **Switch to Desktop** button landing on X11 at source, rather than only shipping recovery paths for it. Yesterday's work diagnosed the cause and added a `wayland` shell function and a desktop shortcut, but both only help *after* you are already in a wrecked-looking session — so the wrong colours came back on the next reboot, which is exactly what happened. Steam invokes `steamos-session-select` **by name through `PATH`**, and `/etc/profile` puts `/usr/local/bin` ahead of `/usr/bin` (verified for `steam.sh`, `steamos-manager` and the gamescope session, which reaches `/etc/profile` via `/usr/share/sddm/scripts/wayland-session`). So `hardware/display/bin/steamos-session-select-shim` is installed as `/usr/local/bin/steamos-session-select` and shadows Valve's copy without editing it — theirs keeps updating normally, where editing it would permanently shadow every future version. It rewrites exactly the bare `plasma` alias to `plasma-wayland` and passes everything else through untouched, so `plasma-x11-persistent` still works if X11 is ever wanted deliberately. `logger`s each rewrite to `journalctl -t steam-machine-session` so the assumption that Steam actually goes through it is checkable rather than assumed.
- Added `hardware/display/systemd/steam-machine-display.service`, because that shim is the first thing in this repo that lives on the **rootfs**. `/usr/local` is part of the subvolume an A/B update replaces wholesale, so the shim is deleted by every SteamOS update — silently, with the first symptom being the colours going wrong again months later and no obvious connection to the update. The unit re-installs it at boot; `/etc/systemd/system/*.service` is on the default keep list, so the unit survives to do the repair. It unlocks the rootfs only when it has work to do and restores `steamos-readonly` to the state it found it in. Verified by deleting the shim, re-enabling `steamos-readonly`, starting the unit, and confirming the shim was back and the rootfs re-locked.
- Left `steamos-readonly` **enabled** afterwards. It had been sitting `disabled` since the `system/rustdesk` install unlocked it and never put it back — the machine had been running with a writable rootfs for days. Installers that need `/usr` unlock on demand, so nothing depends on it staying open.
- **RESOLVED how to clear the 4K120 artefact: a full power-off, never a reboot.** A complete power cycle removed it, and it stayed gone through a boot into Game Mode and a switch into Desktop Mode. Tested and ineffective: warm reboot, reboot to EFI firmware, power-cycling the TV at the wall, unplugging the cable at both ends for 10 s, and switching compositor. The reason a reboot cannot help is that it never cuts the GPU rail — the card is not re-POSTed and the DP-bus-powered converter never loses power, so whatever latched stays latched.
- Added `hardware/display/baseline/seam-present.txt` and `seam-absent.txt`: `--seam` captures either side of that power cycle, at the same 4K120 mode. They `diff` to **nothing**. Same timing, same HBR3 4-lane link, same DSC (on, 16 bpp, 960 slices), same ODM 2:1 at 1922 wide, `underflow 0`, zero link retrains, same DPCD `CH7218 hw 0x03 fw 48.0`. Nothing amdgpu can observe distinguishes a working display from a visibly broken one, which is why so much measurement produced so little. Kept in the repo because the previous captures were in `/tmp` and the power-off wiped them.
- Narrowed the cause to hardware state below the driver — either the GPU's display PHY/link-training calibration (survives a warm reboot, since the card is not re-POSTed) or the CH7218's internal state. Not narrowed further, and deliberately not guessed at again.
- Documented the recovery procedure in the README: shut down and power off rather than reboot, and if it recurs run `--seam` *before* power-cycling and diff against the stored good baseline. An empty diff means stop looking for a software cause.
- **The artefact is at x≈960, not the centre — every earlier entry aimed at the wrong place.** Described first-hand it sits roughly a quarter across, appears in segments rather than as a continuous line, and is only obvious against high-contrast edges (white text on black, bright icon on dark). x=960 is a **DSC slice boundary** (`dsc_slice_width` 960, `dsc_pic_width` 1920 per ODM half → slices at 960/1920/2880), not the ODM stitch at 1920 that this whole investigation had been aimed at. Segmented and content-dependent is characteristic of DSC rate control; a pipe stitch would be continuous and content-independent. This came from the description, not from measurement — no debugfs field distinguishes the good and bad states.
- **DSC is an amplifier, not the cause.** With compression turned off entirely at 4K120 the artefact was *weaker but still present* in the same column. So something else at x≈960 is the source and DSC makes it more visible.
- Recorded two hard limits found while testing. `dsc_bits_per_pixel` **cannot be raised** — writing 288 or 320 does not lighten compression, amdgpu drops DSC altogether, so 16 bpp is the ceiling this link and sink will negotiate and "compress less" is not available. `dsc_slice_width` **cannot usefully be moved** — 480 is rejected and clamped back to 960; 1920 is accepted but reconfigures into a single 3840-wide pipe with one full-width slice that **the TV cannot lock to**.
- **amdgpu's debugfs reports a dead link as healthy**, which invalidates a lot of this file's earlier reasoning. The no-signal configuration above showed `underflow 0`, `clock_en 1` and a clean pipe topology while the TV had no picture at all. Every "underflow 0, nothing wrong" reading recorded here is equally consistent with there being no output, so none of them are evidence the display is good.

Almost all the "DP-to-HDMI 2.1 adapter, vertical line at 120 Hz" material online — including a "line of noise" thread and 4K120 degrading after ~an hour — concerns the CAC-1085, which uses a **Realtek RTD2173**, a different chip. SteamOS loads it itself via its own `ddcutil` and `fwupd` modules-load entries: all 21 `/dev/i2c-*` nodes exist, including the SPD bus. Only the `spd5118` binding stands between userspace and the EEPROMs, and that is bypassable with `I2C_SLAVE_FORCE`.
- Fixed `hardware/coolercontrol/README.md` hardcoding `hwmon4` in the PWM sweep recipe. hwmon numbering is probe-order and moves between boots - `it8696` was `hwmon9` and came back as `hwmon5` after the next reboot. The recipe resolves by chip name.

- Fixed `hardware/sensors/install.sh` skipping the grub drop-in whenever the file merely existed and the parameter was live. Any later edit to the repo's copy silently never reached `/etc` - the installer reported success, changed nothing, and `--status` then showed drift that re-running could not clear. - Fixed `system/rustdesk/install.sh` deriving its LAN allowlist from interface addresses only, so it never saw the RA-advertised ULA (on-link route, no address) and silently dropped RustDesk traffic over it. Now reads routes too and generalises to `fc00::/7` / `fe80::/10`, matching `system/firewall`. pfSense renumbered the ULA a second time during this work (`fde4:...` back to `fd50:...`), which is exactly what the pinned prefixes could not survive.
- Fixed `system/rustdesk/install.sh` adding firewall accepts without removing the previous set, so stale rules accumulated on every prefix change - generalising `fe80::/64` to `fe80::/10` left the old rule behind. `apply_firewall` now reconciles. A re-delegated GUA would otherwise leave an accept for a prefix belonging to somebody else.
- Resolved the `fan5` contradiction in `hardware/sensors/` and `hardware/coolercontrol/`, which documented the case fan as fixed-speed and uncontrollable at ~1548 rpm while it was reading 0 rpm. Both descriptions were right in their moment: the CPU_OPT header was in PWM mode with a 3-pin DC fan, which sees a permanent 12 V and ignores duty. Setting it to Voltage/DC made it controllable but put the BIOS's ~20% duty below the fan's start-up voltage, so it stalls from standstill - forcing `pwm5` to 255 started it at 1513 rpm and it then sustained 1537-1562 rpm back under BIOS control. Whether a cold boot strands it at 0 again is untested and flagged in the docs.
- Fixed `rustdesk.service` failing every boot. `After=NetworkManager.service` waits for the daemon, not for the network: the unit ran 3 s before `enp9s0` got carrier, `lan_cidrs()` found no addresses or routes, and `ExecStartPre` called `die` - so the service was dead until a manual restart, with no firewall rules on 21118 and nothing listening. Found only because the first reboot since install happened. Now ordered after `network-online.target` and `firewalld.service`, with `Restart=on-failure` and a bounded 45 s poll in `--boot`, since IPv6 RA can still arrive after that target is reached.
- Fixed `system/rustdesk/` never appearing in the Desktop Mode application menu. The Arch package ships its `.desktop` files to `/usr/share/rustdesk/files/` and relies on `.INSTALL`'s `post_install()` to copy them into `/usr/share/applications/`. We exclude `.INSTALL` deliberately - it also overwrites our unit and runs `systemctl enable/start` - but never replicated the desktop-file copy. With no menu entry the obvious move is to install the Flatpak, which lands at `/app`, fails rustdesk's `is_installed()`, keeps a separate config and ID, and competes for 21118. `--status` now reports both the missing entry and any Flatpak alongside it.
